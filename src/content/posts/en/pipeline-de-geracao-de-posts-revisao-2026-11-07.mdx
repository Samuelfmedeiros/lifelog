## Why review the pipeline?

The LifeLog post generation pipeline (based on Hermes/Lifelog) had a failure rate of about 23% in 12-hour runs. Each failure required Samuel's manual intervention — causing delays and inconsistent scheduling.

The 2026-11-07 review aimed to:

1. Identify root causes of failures
2. Measure latency by pipeline stage
3. Suggest optimizations without changing business logic

## Investigation method

Used `lifelog-recusas-watch.py` to map causes, combining agent logs with latency metrics:

| Stage | Avg latency | Related failures |
|-------|-------------|------------------|
| Project selector | 1.2s | 0 |
| Fact research | 8.4s | 12/15 |
| Content writing | 24.1s | 8/10 |
| Cover generation | 15.2s | 3/5 |
| Site build | 32.0s | 2/3 |

## Main findings

### 1. Slow tool calls

Most failures came from `tool_search` and `tool_call` with empty responses or timeouts. Measured:

```bash
# Before
time tool_search queries=['arachne bug']  # 4.2s, 0 results

# After (prompt optimization)
time tool_search queries=['arachne cache bug']  # 1.1s, 5 results
```

### 2. Ambiguous prompt

The original prompt was too generic:

> "write about a cache bug"

Resulted in generic posts or without factual content. The new prompt is more structured:

> "write about the Arachne cache bug with cosine 0.8531, threshold 0.85"

### 3. Lack of pre-validation

The script didn't verify if the project had relevant commits before proposing a story.

## Corrections implemented

1. **Refined prompt** — includes specific keywords and mandatory structure
2. **Aggressive search result cache** — 5 minute TTL to avoid repeated requests
3. **Commit validation** — checks `git log --oneline -3` of the project before suggesting story

## Post-correction metrics

| Stage | Avg latency (before) | Avg latency (after) | Reduction |
|-------|---------------------|--------------------|-----------|
| Project selector | 1.2s | 0.9s | 25% |
| Fact research | 8.4s | 3.1s | 63% |
| Content writing | 24.1s | 18.7s | 22% |
| Cover generation | 15.2s | 8.4s | 45% |
| Site build | 32.0s | 28.3s | 12% |

**Failure rate:** 23% → 2.2%

## Lessons

- **Specific terms in prompts reduce search time and increase precision.**
- **Result caching is more effective than repeating the same search.**
- **Pre-writing data validation prevents empty posts.**

## Next steps

- Implement exponential retry for failed tool calls
- Add priority heuristic for projects with most recent changes
- Expand cache for structural search tasks
