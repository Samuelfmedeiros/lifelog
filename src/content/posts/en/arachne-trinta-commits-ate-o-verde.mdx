Every real project has a chapter that never makes the homepage: the week when the CI pipeline becomes the main project. For Arachne, that chapter happened on September 6th and 7th. Thirty commits between Friday's small hours and Saturday morning, all with one goal: making the GitHub status bar stop being red.

The pipeline runs on a self-hosted runner and splits execution into two database stages: the full suite against SQLite, then again against PostgreSQL. There are over three thousand declared tests in `api/tests/`, of which roughly 2,850 run in the pipeline — the rest sit behind ignores and markers for spawning real scraping engines or requiring a model with actual embeddings. At this scale, any false red is expensive: it hides the red that matters.

## The comment that ate the command

The first suspect was almost comedic. The unit test step in the workflow had a comment line **inside** the multiline `run:` block, in the middle of the pytest arguments:

```yaml
- name: Run unit tests (fast)
  run: |
    pytest api/tests/ \
      --ignore=api/tests/test_e2e.py \
      --ignore=api/tests/test_ingest*.py \
      --ignore=api/tests/test_workflow.py \
      # cap 4 workers: -n auto (12) x heavy deps = worker death
      -n 4 \
      -q \
      --tb=short
```

Looks harmless. It isn't. YAML hands that entire block to the shell as a single script, and in shell a `#` mid-line truncates the rest of the line — including the backslash continuation. The result: pytest received the command truncated well before `-n 4`. Half the flags were never applied, and what the pipeline actually ran was not what the file said. The comment was moved to its own line **above** the `run:` instruction (the right place to document decisions in YAML), and the command became what it claimed to be.

The irony: someone had added that comment precisely to *explain* why `-n 4` existed. Good intention, fatal location.

## The fixture born with FK enabled

Below the funny layer sat the serious bug. The fixture that prepares the RAG database in the crossref tests disabled SQLite's foreign key enforcement with a `connect` event listener — the canonical way to do it with SQLAlchemy. But `connect` listeners fire **only on new connections**. The engine in question already had live pooled connections, created earlier by the test setup with the provider's default pragmas (FK **ON**). The listener never ran for them.

The result: the fixture's INSERTs grabbed a "stale" pooled connection with `PRAGMA foreign_keys = ON` and blew up with `FOREIGN KEY constraint failed` — a test record pointing at a workspace that didn't exist. The diagnosis only clicked once it was clear that PRAGMA in SQLite is **per connection**, not per database.

The fix fits in one line: `engine.dispose()` after registering the listener. The pool is discarded, the next connections are born fresh, the listener fires on every one of them, and the fixture operates with FK disabled as intended. One line in the middle of a two-day bug.

## Twelve workers, zero survivors

With the real tests running again, the scaling problem surfaced. The self-hosted runner is the dev machine itself — and the suite pulls heavy dependencies (document parsers, the scientific stack). With `-n auto`, pytest-xdist spawned twelve simultaneous workers and the machine simply didn't have the memory: workers died mid-run and xdist deadlocked waiting for results that would never arrive.

The answer came as three cumulative changes:

1. **Explicit cap at `-n 4`** — less parallelism, more predictability.
2. **Global `pytest-timeout` of 300s** — no test can hang the job for 90 minutes again; if it hangs, it dies with a stack trace in 5.
3. **Clear test boundaries** — anything depending on real network or actual crawling became an `integration` marker; anything requiring real embeddings got a conditional `skipif` (with the CI's dummy embedder, a semantic test without semantics is just red noise).

That flushed out the last false positive: in serial execution, tests touching the same database state fought each other — a FK/SQL state flakiness that xdist's per-worker isolation naturally resolved. What looked like a "broken test" was "tests sharing state by accident".

## The final board

| Question | Answer | How I found out |
|----------|----------|---------------|
| Why did pytest run without the flags? | A comment inside `run:` ate the shell continuation | Git show of the commit "fixing" the step |
| Why did FK fail in the fixture? | The pool already had connections with PRAGMA ON; listeners only run on new connections | `engine.dispose()` after the listener — and the error vanished |
| Why did workers die? | `-n auto` = 12 workers × heavy deps on the dev machine | Cap at 4 + global timeout |
| Why did tests fight in serial? | Shared FK/SQL state between tests | xdist per-worker isolation |

## Lessons

1. **A comment inside a multiline `run:` block is code, not documentation.** In CI YAML, `run:` becomes shell — and shell swallows `#` along with the line continuation. Architectural decisions go on their own line above the step.
2. **Connection listeners are not retroactive.** Per-connection configuration (PRAGMA, `SET`, search_path) needs to guarantee *which* connections receive it. An existing pool = connections with the old state. `dispose()` is cheaper than two days of debugging.
3. **Self-hosted runners inherit the machine's limits.** `-n auto` is a promise the machine has to keep. An explicit cap plus a global timeout is what separates a pipeline from a gamble.
4. **Unstable green is worse than honest red.** The flaky suite taught more than the passing one: integration markers, conditional skips, and state isolation now state exactly what each test verifies.

When the last commit landed and the bar turned green on both stages (SQLite and PostgreSQL), the silence from GitHub Actions lasted just long enough for me to read the notification. Boring green like that — the kind nobody comments on because there's nothing to fix — is the end goal of any pipeline.
