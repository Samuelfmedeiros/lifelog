## The tag cloud became a babel

The archive's tag cloud mirrored this blog's biggest sin: every post was
free to invent its own taxonomy. "automacao" here, "automation" there,
"Automação" elsewhere — three chips pointing at concepts that, in my head,
were one and the same. The `/tag/<slug>` pages from Option C finally
existed, but they fed on a swamp: 336 live slugs and nothing stopping the
next post from adding the 337th with a typo.

The campaign's trigger was a Dogwalk post. I wrote the frontmatter on
conviction — tags [pwa, service-worker, offline, workbox, front] — and CI
broke on the pipeline. The old check only shouted after the push.
Vocabulary validation isn't a build report; it's a gate: it must reject
before merge, otherwise yesterday's exception becomes today's rule.

## The decision: one vocabulary, two languages

Option C beat the other two with a simple argument: whoever maintains the
vocabulary is the same code that consumes it. The source of truth became
a TypeScript file the UI imports directly — zero drift between what the
gatekeeper validates and what the chips render. No manual mirror, no
divergence.

The language rule was the part that took the most back-and-forth with
myself. Canonical slug in English (technical lingua franca), but with a
Portuguese label for display: the slug is `security`, the visitor reads
"Segurança". The Portuguese variant never becomes a slug — it becomes an
alias pointing to the canonical one. One concept, one slug, N entry
paths.

```typescript
export const TAG_VOCAB: TagDef[] = [
  { slug: 'security', pt: 'Segurança' },
  { slug: 'automation', pt: 'Automação' },
  // ...
]

export const TAG_ALIASES: Record<string, string> = {
  'seguranca': 'security',   // PT variant = alias, never a slug
  'automacao': 'automation',
}

export function canonicalizeTag(tag: string): string {
  const key = tag.trim().toLowerCase().replace(/_/g, "-").replace(/\s+/g, "-");
  const c = TAG_ALIASES[key] ?? key;
  return c in TAG_ALIASES ? TAG_ALIASES[c] : c;
}
```

## The gatekeeper that speaks the same language

The CI gatekeeper is a Python script — and the part that gave me chills
was duplication: if the validator reads the vocabulary from a copy, drift
between copies becomes a silent bug. The solution: the gatekeeper
**parses the .ts itself** — regex extracts slugs and aliases straight
from the file the UI consumes. One source of truth, two consumers.

The error codes became a mini-dictionary of what goes wrong in taxonomy:
E1 (tag outside the vocab), E2 (missing project tag — the structural
one), E3 (PT and EN diverging), E4 (multi-line tags, another frontmatter
parse poison), E5 (duplicate within a post), E6 (project outside the
vocab). With `--strict`, any E rejects the deploy.

```yaml
# .github/workflows/deploy.yml — quality gates, before the build
- name: PT/EN Sync check
  run: python3 scripts/check-lang-sync.py
- name: Tag vocabulary check (Opção C)
  run: python3 scripts/check-tags.py --strict
```

And a CI lesson that cost one round: the gatekeeper lives in the
repository, but CI runs on the GitHub runner — an absolute path from my
machine broke everything at checkout. `ROOT = Path(__file__).resolve().parents[1]`
resolves relative to the script and works in both worlds.

## 269 files in one migration

With vocabulary and gatekeeper ready, the boring part remained: existing
posts. The migration touched 269 PT and EN files — canonicalizing
aliases, enforcing the project's structural tag, unifying PT/EN,
deduplicating, and flattening everything to a single line in the
frontmatter (multi-line tags were yet another silent parse poison).

The parity criterion was the detail that made the migration worth it: PT
and EN of the same post now have **identical** slugs, in the same order.
The /tag/security page shows the same set of posts in both languages —
if they ever diverge, E3 flags it in CI.

## What I learned along the way

**The comparison that sealed the decision:** options A and B treated tags
as free text with hints; Option C treats them as schema. The difference
showed up in the first new post after the gatekeeper — I typed `front`
from memory, the gatekeeper pointed to the canonical (`frontend`), and
the new concept (`metadata`, `taxonomy`) entered the vocab in the SAME
commit as the post that uses it. New concept without a vocab entry = red
CI. Legislation grows along with the city, never after.

**A new concept is a design decision, not a typo to fix on the fly.**
The moment to add a slug is the same as the post that introduces it — it
forces the question "is this a recurring theme or a one-off?" 336 slugs
in, the vocabulary stays canonical, bilingual and guarded.
