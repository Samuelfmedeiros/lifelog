At some point in every fine-tuning run you have to pick a checkpoint. The ruler almost everybody reaches for is the same one: `eval_loss`, or its teacher-forced cousin, `held_loss`. Lowest number wins. You select it, export it, ship it.

The number went from **9.09 down to 8.38**. It looks like a win. It is exactly the scenario where the model got worse.

## What the metric cannot see

`held_loss` measures one thing: how well the model answers on the held-out set you kept aside. It does not measure the other thing — how much it **forgot** what it already knew before you arrived.

In the run this post comes from, held loss fell 9.09 -> 8.38 while an earlier capability, English, **degraded by +103%**. The number used to approve the checkpoint got better at the same time the model actually got worse. Both facts are compatible: improving one set does not mean keeping the others.

## The tool that measures the other half

[ForgetGate](https://github.com/Samuelfmedeiros/forgetgate) is built around a simple claim: a checkpoint is not better because it is lower on one number, it is better because it did not forget. The scorecard it produces carries held loss and regressed probes together, and states the verdict in one word a CI pipeline understands: `keep`, or `abort`.

Zero dependencies, twenty tests, and an exit code a pipeline can gate on. The core decides; whoever trains just obeys the verdict.
