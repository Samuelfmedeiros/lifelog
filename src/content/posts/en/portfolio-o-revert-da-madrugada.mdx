## Saturday, 3:55 AM

There is a kind of commit that only happens before dawn. Nobody discusses it on a call, nobody reviews it calmly — it's that executive commit, from someone who decided it needs to leave the tree *now*, before bed.

On Saturday, at 3:55 AM, the portfolio got one of those:

```bash
$ git log -1 --format="%h %ad%n%s"
4dd1a99 Sat Sep 5 03:55:42 2026 -0300
Revert "Merge pull request #72 from Samuelfmedeiros/feat/perf-bundle"
```

PR #72 was V5 of the resume tailor — the tool that analyzes a résumé against a job posting with AI and generates a tailored PDF. The revert removed it entirely. It didn't disable it, didn't hide it behind a flag: **it took it out of the tree**.

## What left the tree

The revert's `--stat` tells you the size of it:

```text
 20 files changed, 2363 insertions(+), 4819 deletions(-)
```

Four thousand eight hundred lines, out. The API route (`route.ts`, 360 lines), the full modal with tests (386 + 195), the guardrails with tests (412 + 296), the PDF generator with tests (588 + 160), the resume data, the brand colors, a hydration hook. Everything the feature was, plus everything that proved it.

A revert isn't a delete — history is still there, one line of `git log` away. But the practical effect is the same as erasing: the next deploy doesn't know the feature. The whole project spent the week without it.

## The week without the feature

Here lies the part nobody documents: what a clean revert leaves behind.

The site worked. No broken route, no orphan import — the revert was surgical. But the feature left three debts hanging:

- **The tests left with it.** Nearly a thousand lines of tests stopped running. Coverage isn't just a number: it was the proof that PDF, guardrails and modal behaved.
- **The question stayed open.** The revert doesn't say "this feature is bad" — it says "this version doesn't stay." The difference between the two sentences is the next week's work.
- **The original problem kept standing.** The AI route V5 solved didn't stop existing; it stopped having a solution in the tree.

A well-made revert is an implicit promise: *this comes back, but not like this.* If it were final, it would be removal with a funeral — changelog, deprecation, notice. A dawn revert is the opposite: urgency to pull out, conviction it can be done better.

## Friday, 12:18 AM — the return

Six days later, before dawn again (apparently it's the official time for this kind of decision), V5 came back:

```bash
$ git log -1 --format="%h %ad%n%s"
d247a55 Fri Sep 11 00:18:59 2026 -0300
feat(resume-tailor): V5 reintroduced with LLM chain and loud failure
```

```text
 14 files changed, 3242 insertions(+), 172 deletions(-)
```

If the commit had been a `git revert 4dd1a99`, the story would end here and wouldn't be worth a post. But the reintroduction brought 14 files with different decisions — it came back **better**, not the same. Three of them are worth recording.

## Decision 1: the model race is over

The removed version kept a hardcoded list of free models from an aggregator in the route — and raced them in parallel, hoping one would answer within the timeout:

```typescript
const LLM_MODELS: { model: string; maxTokens: number }[] = [
  { model: "minimax/minimax-m3:free", maxTokens: 2200 },
  { model: "nvidia/nemotron-3.5-lightning:free", maxTokens: 2200 },
  { model: "cohere/north-mini-code:free", maxTokens: 2200 },
];
// parallel race: first to answer wins, 20s individual timeout —
// a congested free model can't hold up the queue
```

It works until it doesn't. A free model disappears, renames itself or wakes up congested — and the route is a race code with an outdated entry list. Every new model was one more line to maintain, and the paid fallback only kicked in when *all* the free ones failed (a balance-protection that was also a bet).

The new version swapped the race for a **provider chain**:

```typescript
async function tryProviders(prompt: string): Promise<string> {
  try {
    const out = await callArachneLLM(prompt);   // ecosystem gateway
    return out;
  } catch (err) {
    errors.push(`arachne: ${err.message}`);
  }
  if (process.env.RESUME_LLM_URL) {
    const out = await callDirectLLM(prompt);    // direct fallback (dev)
    return out;
  }
  throw new LLMUnavailableError(errors.join(" | "));
}
```

The portfolio no longer knows which models exist. It talks to a gateway — which in turn orchestrates providers, rotation and rate limiting — and has a direct URL fallback for the dev environment only. When a model dies, it dies at the gateway; the route never even hears about it. **AI infrastructure integration is an address, not a list.**

## Decision 2: fail loud

The old version had a behavior I now consider a crime: when the LLM response came back imperfect, the code tried to *sanitize* whatever came — trim highlights, adjust fields — and returned the PDF anyway. The user received a plausible-looking document built on partial data. The reintroduction commit message sums it up: "LLM unavailable now answers 502 (before: placeholder PDF with HTTP 200)".

The new version separates two worlds:

```typescript
// LLM unavailable → explicit error
throw new LLMUnavailableError("gateway did not respond");

// ...
} catch (err) {
  if (err instanceof LLMUnavailableError) {
    return NextResponse.json({ error: "The AI is unavailable right now." },
      { status: 502 });
  }
}
```

A 502 is uglier than a placeholder PDF — in the feelings of whoever is testing. But placeholders are compound interest: the user thinks that empty document is the product's real capability, and you find out about the problem from a recruiter's report. **An honest failure is a feature. Today's explicit error is tomorrow's well-filled ticket.**

## Decision 3: the anti-echo guard

Small free LLMs sometimes "answer" one specific thing: the prompt's own template. You ask for a JSON with an example — `"role adjusted for the job"`, `"skill1"`, `"bullet1"` — and it returns the example, formatted, convinced it did the task.

The dangerous part is that this echo easily passes structural validation: every field is there, the JSON parses, the PDF renders. But it's theater — a résumé listing `skill1` as a skill.

The new version carries the list of echo markers and treats it as an AI failure:

```typescript
const PROMPT_ECHO_MARKERS = [
  "ajustado para a vaga",
  "resumo profissional reescrito",
  "skill1", "skill2",
  "bullet1", "bullet2",
  "competência1",
];

export function looksLikePromptEcho(text: string): boolean {
  const t = (text ?? "").toLowerCase();
  if (!t.trim()) return false;
  return PROMPT_ECHO_MARKERS.some((m) => t.includes(m));
}
```

In the route, the flow is: echo detected, repeat the request with a reinforcement appended to the prompt ("DO NOT repeat the example values — fill in the REAL resume data"). Echoed again? 502, no PDF. The rule that stuck: **validating content is different from validating structure — and the second never replaces the first.**

## What a revert buys

| | Revert (Saturday) | Reintroduction (Friday) |
|---|---|---|
| Time | 3:55 AM | 12:18 AM |
| Commit | `4dd1a99` | `d247a55` |
| Lines | −4,819 | +3,242 |
| Files | 20 | 14 |
| AI integration | hardcoded race of free models | provider chain via gateway |
| LLM down | sanitized partial PDF | explicit 502 |
| Prompt echo | became theatrical PDF | guard + retry + 502 |

The revert and the reintroduction don't cancel each other out. The first cleaned the tree and bought time; the second used the time to come back with a different architecture. If V5 had come back identical, the six days would have taught nothing — it would have been just an undo with extra steps.

The lesson for the next feature that grows too fast: a revert isn't the opposite of shipping. It's the half of the cycle that guarantees the other half can happen again.
