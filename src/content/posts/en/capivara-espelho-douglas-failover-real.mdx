## ⚡ The personal hub that can't go down

Capivara is the command center of my ecosystem: dashboard, service health checks, Umami, admin for everything, Second Brain. If it goes down, **everything looks dead** — even when the other projects are standing.

In August 2026, it was returning **intermittent 502s** on the tunnel. It wasn't a crash — it was worse: invisible downtime that appeared and disappeared. The answer was the architectural principle that applies to the whole ecosystem: **Douglas = mirror + fallback**. And to prove it worked, we did the most honest test there is: we took down the primary service on purpose.

## 🧠 Context — the 502 that came and went

Capivara runs on Samuel: FastAPI on port 8001, Cloudflare Tunnel exposing `capivara.seu.pet`. Douglas is the ecosystem's mirror/fallback PC — the same role it already plays for Arachne and Dogwalk.

The problem: the tunnel was answering **200/502 alternating**. One healthcheck caught 200, the next caught 502. To the user (me), it was "sometimes it works". To the system, it was a single point of failure with no coverage.

The ecosystem rule: **if Samuel OR Douglas goes down, the site stays up**. Capivara wasn't following that rule yet.

## 🔧 The struggle — building the mirror

The implementation (Option A — full mirror, decided on 03/08/2026) was surgical:

1. **Backend copied to Douglas** — same path, Python 3.13.5 venv + extra deps (httpx, psutil, pyotp, qrcode, pywebpush, chromadb). The `requirements.txt` was outdated — the copy forced the real list (commit `9477700`)
2. **frontend/dist copied** — the whole SPA
3. **Identical service** — `capivara-backend.service` (127.0.0.1:8001, EnvironmentFile .env, **SAME JWT secret** — both sides accept the same tokens)
4. **Douglas's tunnel** — `capivara.seu.pet → 127.0.0.1:8001` in its cloudflared config
5. **One-way DB sync** (Samuel → Douglas), via a dedicated script:

```bash
# capivara-db-sync-douglas.sh — consistent snapshot even with the app running
sqlite3 capivara.db ".backup /tmp/capivara_sync.db"   # snapshot
scp /tmp/capivara_sync.db samuel@192.168.7.5:C:/Temp/  # transfer
# on Douglas: stop service, swap db, start again
```

6. **Healthcheck** — 5-minute timer on Douglas to make sure the service stays alive

The sync uses **SQLite delete mode (no WAL)** — a `.backup` snapshot is consistent even while the app is writing. A detail that avoids corrupting the database mid-copy.

Right after setting it up, the immediate test: `/health` **10/10 = 200** through the tunnel with Douglas active (before: 200/502 alternating).

## 💡 Resolution — the failover that worked on its own

The final proof was the **real failover test**: Samuel's cloudflared was **stopped for ~40 seconds**. Nothing touched on Douglas.

Result:

```
capivara.seu.pet → 5/5 = 200  (Douglas took over ON ITS OWN)
dogwalk uptime: 61024 → 61104  (proof that the origin switched to Douglas)
turned Samuel's cloudflared back on → 5/5 = 200
```

The coolest detail: the proof didn't come from a Capivara log — it came from **Dogwalk's uptime counter**, which tracks where the response came from. The counter jumped to Douglas at the exact moment of failover and came back when Samuel reconnected. High availability validated for real, not in theory.

## 📊 Metrics

| Metric | Before | After |
|--------|--------|-------|
| Tunnel | 200/502 alternating | 5/5 = 200 stable |
| Failover | didn't exist | automatic (Douglas takes over in ~40s) |
| Response origin | Samuel (only) | Samuel + Douglas (mirror) |
| DB sync | didn't exist | one-way Samuel → Douglas (1h cron) |
| Healthcheck | — | 5-min timer on Douglas |
| Dogwalk uptime | single origin | 61024→61104 (proof of switch) |

## 🎯 Lessons

1. **Availability is PROVEN, not promised** — a real failover test (take down the primary and watch the mirror take over) is worth more than any documented architecture.
2. **The mirror must be identical down to the secret** — same JWT secret on both sides means user tokens survive the failover with no re-login.
3. **One-way sync with a consistent snapshot** — `sqlite3 .backup` + swap avoids database corruption. SQLite delete mode (no WAL) simplifies the sync.
4. **The proof can live in the neighbor** — Dogwalk's uptime proved Capivara's failover. Cross-service observability is a superpower.
