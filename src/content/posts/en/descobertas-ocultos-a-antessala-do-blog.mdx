## The list that had nothing inside

Every empty list has two possible meanings: "there is nothing here" or "I couldn't look". The problem is that the API response is the same for both — and that is exactly the hole that cost me an entire day of useless debugging.

The route in question listed content pending moderation on my blog. Locally, under `pnpm dev`, it worked: it filled up, listed items, shrank as I made decisions. On the deploy, it returned an empty array. Always. No log, no stack, no error status — a `200 OK` with an orphan list inside.

I spent that first day hunting the bug in the wrong place: **the data layer**. Tweaked the query, checked the filter, re-read the permission logic. If the list came back empty, it was because there was nothing to list, right?

Wrong. The data existed. What was missing was the *read* — and nobody, not the log, not the page, not me, was in a position to know.

## The try/catch that lied to me

The cause, once I found it, fit in one line: the content-directory read used a path relative to the runtime package. Locally, the code runs inside the repository tree and the path exists. On the deploy, the route code gets bundled into a serverless chunks directory where that tree simply doesn't exist.

And the broken path had a bodyguard:

```javascript
// the pattern that turned a crash into a mystery
let items = []
try {
  items = readDirectory(pathThatDoesNotExistOnDeploy)
} catch {
  // "if it fails, show an empty list" — the most expensive sentence I ever wrote
  items = []
}
```

The `try/catch` wasn't wrong for existing — it was wrong for its **implicit contract**. It said: "a failed read is the same as absence of content". And to the route's consumer (the moderation page, and me staring at it), the two states were indistinguishable.

The crash I *wanted* to have — stack trace in my face, red build, an error screaming — was converted, by one line of "robustness", into the slowest failure there is: one disguised as valid data.

## The taxonomy my vocabulary was missing

After fixing it, I stopped to name what happened — because "bug" doesn't describe enough:

| Failure type | Symptom | Time to discover | How it shows up |
|---|---|---|---|
| Explicit crash | error, stack, status 500 | minutes | in your face, in the log |
| Wrong data | incoherent value on screen | hours | when someone notices |
| **Error as absence** | **a valid, empty state** | **days** | **never — it looks right** |

The third category is the most dangerous of the three, and the one that least appears in checklists. A crash is embarrassing but honest. Error-as-absence is a bug pretending to be a legitimate system state — and every observer (log, monitor, human) approves the disguise again, because the response is *structurally valid*.

The detail that still bothers me: if that `catch` didn't exist, the deploy would have failed **immediately**, with the exception pointing at the exact directory. My "protection" against errors turned a 30-second failure into an 8-hour one.

## The rule I adopted: no emptiness without justification

The bug fix itself was simple — freeze the list at build time, turning a runtime read into a static import (the subject of the previous post). But the permanent change was a design rule I've carried since:

**An endpoint may only return an empty collection if it knows the data source is healthy.**

In practice, three layers:

1. **Distinguish "genuinely empty" from "the read failed"** — if the read can fail, the result is not `[]`, it's a typed error (or an object with `healthy: false`). The page decides what to show with truthful information.
2. **Fail loud and early** — if the data is known at build time, verify it at build time. A broken build is cheap; silence in production is expensive.
3. **Log the bad path** — every `catch` that doesn't rethrow must, at minimum, record what it swallowed. An empty `catch` is a scheduled bug.

The moderation panel now has three states, not two: full list, empty list with a healthy-source badge, and error state. The third one only had to appear once to be worth the effort.

## What stuck

| Before | After |
|---|---|
| `catch` → `[]` (indistinguishable from a real empty) | typed error kept separate from an empty collection |
| data rediscovered at runtime (fragile path) | data frozen at build, static import |
| silent failure in production | build fails in front of you |
| 8h of blind debugging | minutes: the failure points at its own path |

The previous post in this series covered the solution to the problem (building the data at build time). This one covers what the error taught me about the code itself: **the enemy wasn't the relative path — it was the disguise the error was wearing.**

Robustness without observability isn't robustness, it's theater. The catch you write to "keep the page from breaking" will break — it just picks the most expensive moment and the worst disguise.
