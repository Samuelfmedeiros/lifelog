## The route that worked on my laptop

Any site with moderation has, somewhere, a page only the owner should see: what awaits a decision. Mine listed the blog's pending content — and it worked perfectly under `pnpm dev`. On the deploy, it returned an empty list. Always. No error log, no stack trace, just emptiness.

The first line of code on that route was innocent enough:

```javascript
// what I wrote first — works locally, breaks on deploy
import { readdirSync } from 'fs'
const dir = path.resolve(__dirname, '../src/content/posts')
```

Locally, `__dirname` points to the right place: the code runs inside the repository tree, and the content files sit two levels up. That exact assumption is what broke on the deploy.

## The bundle doesn't preserve the repository tree

On a serverless deploy, route code gets *bundled*: the functions are packed into a chunks directory, far from any `src/content/`. The `__dirname` that pointed into the repo tree on my laptop pointed at a folder that will never contain a content file.

And the worst part came from my own "robustness": the `try/catch` I wrapped around the read swallowed the exception and returned an empty list. The worst kind of failure isn't the one that explodes — it's the one that disguises itself as missing data. The page said "nothing pending" when the truth was "the read never happened".

Lesson registered: if an error is handleable, handle it loudly; if it isn't, let it propagate. Silence isn't robustness, it's sabotage against your future self.

## The way out: freeze the data at build time

The fix came from a principle the static generator itself already teaches — if the data is known at build time, there is no justification for rediscovering it at runtime:

```javascript
// scripts/gen-data.mjs — runs BEFORE the build
// 1. scans the content tree with gray-matter (parses only the frontmatter)
// 2. extracts slug, title, date and project for anything matching the criterion
// 3. writes api/data.mjs: export default [ ...items ]
```

The serverless route stopped touching the filesystem and became a plain `import`. The data travels *inside* the bundle, generated by whoever has full context: the build machine. `__dirname` — the fragile piece — vanished from the runtime code entirely.

| | Read at runtime | Freeze at build |
|---|---|---|
| `__dirname` | geographic gamble | doesn't exist |
| Data source | server, on request | build machine |
| Typical failure | silent empty list | build breaks in your face |
| Cost per request | read + parse | static import |

The middle column isn't just slower — it's *unsound*. The right one fails early and loud, which is where failures should fail.

## The moderation panel that gained a complaint desk

With the data frozen, the moderation page became what it should always have been: a list of what awaits a decision, and a button per item. The next step is already live — the "reject" button on an approved-failed item opens an issue on the repository, with the reason written on the spot, and sends the item back to the review queue.

The loop is closed: the pipeline produces, the page lists, the decision back becomes a traceable artifact in the repository. Moderating stopped being a terminal ritual and became two taps — with an audit trail for free.
