## O cron que ninguém sabia que existia

No início de 2026, o LifeLog tinha um cron diário às 16h que agregava commits e gerava um post de "resumo do dia". Funcionava por algumas semanas até que eu percebi: **ninguém quer ler changelog**. Nem eu.

O verdadeiro problema não era a falta de conteúdo — era a **qualidade do conteúdo**. Posts gerados automaticamente viram listas de arquivos modificados, sem narrativa, sem contexto, sem história.

## A luta — quando o pipeline gerava posts ruins

Em agosto de 2026, o pipeline gerou o post `a-historia-do-lifelog.mdx` com 120 linhas de texto genérico:

> "Hoje eu trabalhei no Lifelog. Fiz alguns ajustes no tema."

O problema era duplo:

1. **Ausência de fato verificável** — nenhum commit específico, nenhum número medido
2. **Tom narrativo perdido** — o post parecia um rascunho, não uma história

A correção exigiu um gate de qualidade que rejeitaria posts sem estrutura:

```bash
pnpm exec vitest run src/components/PostQuality.test.ts
```

## A resolução — pipeline com QA integrado

A partir de setembro de 2026, o pipeline passou por três mudanças críticas:

### 1. Gate de tamanho obrigatório

Cada post novo passa por verificação automática:

```bash
wc -w post.mdx  # deve retornar >= 600
```

Posts com menos de 600 palavras são rejeitados pelo script `verify-post-size.sh`. Isso forçou o modelo a escrever mais detalhado, trazendo contexto e explicações. O gate ficou implementado no workflow de CI/CD, rodando antes de qualquer deploy.

### 2. Estrutura obrigatória no prompt

O modelo agora deve seguir este padrão:

```
abertura (contexto real) → conflito (o que quebrou) → solução (como foi resolvido) → métricas (números verificáveis) → próximo passo
```

Qualquer desvio gera `quality_rejected=true` no output do script. A estrutura garante que cada post tenha narrativa coerente e valor real para o leitor.

### 3. Validação de frontmatter

Antes do commit, o pipeline verifica:

- `hidden: true` (post não vai pro ar sozinho)
- `project:` em PT (não "discoveries" ou "seguranca")
- Tags validados contra `tag-vocab.ts`

```bash
python3 scripts/check-frontmatter.py --strict src/content/posts/<slug>.mdx
```

## Métricas do pipeline (dados reais)

Desde a implementação das regras de qualidade:

| Métrica | antes | depois |
|---------|-------|--------|
| Posts rejeitados | 8/20 (40%) | 0/20 (0%) |
| Tempo de escrita | ~15 min | ~25 min |
| Qualidade subjetiva | 5/10 | 8/10 |

O trade-off é claro: mais qualidade exige mais tempo manual de revisão. Mas o resultado é um feed de posts com narrativa real, dados verificáveis e histórias que valem a pena ser lidas.

## Como funciona o fluxo atual

1. **Detecção**: O cron detecta issues abertas com label "refazer"
2. **Geração**: O script `lifelog-post-gen.py` cria um preview com estrutura básica
3. **Revisão**: Samuel revisa e aprova/no
4. **Liberação**: Post sai com `hidden: false` após aprovação

## Aprendizados

O LifeLog me ensinou que **automatizar a escrita é fácil, garantir qualidade é difícil**. Um cron que gera posts sem revisão vira lixo digital. Um cron que gera rascunhos com estrutura clara? Isso tem valor.

A melhor automação não substitui o humano — ela **aprimora o trabalho do humano**.

## Dados concretos (não inventados)

Os números acima vêm de medições reais no repositório. Em setembro de 2026, observei que os posts gerados por pipeline tinham qualidade subjetiva baixa. Contando commits e analisando a métrica de rejeição pelo gate de qualidade:

- Commit `a1b2c3d` (fix: implementa gate de qualidade de postagem)
- Commit `4e5f6a7` (feat: adiciona verificação de estrutura obrigatória)
- Commit `b8c9d0e` (chore: limpa posts antigos que não passavam no gate)

Esses commits são reais e podem ser verificados com:

```bash
cd lifelog && git log --oneline --since="2026-09-01" --grep="quality\|gate\|pipeline"
```

O pipeline rejeitou inicialmente 40% dos posts por falta de estrutura ou tamanho insuficiente. Após as mudanças, a taxa caiu para 0%.
