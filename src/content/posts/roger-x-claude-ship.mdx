## 1. O dia em que a Anthropic lançou um revisor

Em 23 de novembro a Anthropic lançou o **Claude Ship**: Code Review em GA, PR Steward e Approvals em beta, tudo dentro do GitHub e dos planos Team e Enterprise.

É um pacote bom. Polido, com auto-fix pronto — o PR Steward faz push da correção, o Approvals aprova, e o check run aparece no pull request como qualquer outro gate. Quem nunca construiu um revisor de código olha para aquilo e pensa que o problema está resolvido.

Eu olhei e reconheci a maior parte das peças. Fazia meses que elas rodavam aqui.

## 2. Contexto: por que o Roger existe

O Roger nasceu do loop de entrega dos meus projetos. O problema não era "ter um revisor de IA" — era ter um revisor que servisse a **qualquer** repositório meu, sem GitHub App, sem plano Team, sem mandar código para a infraestrutura de outra empresa e sem pagar por token de agente que eu já tenho rodando localmente.

Ele é o motor que fecha o ciclo: recebe a entrega, roda o critic, mede, dá nota, anexa evidência e decide se aquilo pode seguir. Quando não pode, ele não conserta — ele explica. Causa, correção sugerida e rollback, para uma pessoa decidir.

Essa última frase é a arquitetura inteira. Não é uma configuração que dá para desligar no painel.

## 3. O que já estava no código — com data

Vale ser preciso sobre o que existia antes do Ship, e sobre onde isso está documentado.

- **02/09 — v2**: branch de campanha, KB e regressões. O revisor deixou de ser um script que opina e virou um ciclo com memória do que já falhou antes.
- **03/09 — v3**: painel A+B+C, auto-heal e cobertura. O motor passou a se recuperar de fase travada em vez de morrer calado.
- **02/11 — `_anexar_estado_main`** (linhas 4903–4995 do motor): mede conflito **real** com `merge-tree`, classifica o que chegou entre entrega, sujeira e ressurreição, e recomenda. O merge continua humano.
- **10/11 — eixo duplo Standards × Spec, fail-closed**: dois eixos independentes de avaliação. Se um deles não consegue medir, o veredito não é "aprovado com ressalva" — é bloqueado.

Uma nota de método: o repositório versionado começa em **15/10**, por causa de um restore. As datas de setembro vêm do cabeçalho do motor vivo (`loop_orchestrator_unified.py`, linhas 66–76), não de commit. Então o certo é "documentado desde 02/09", nunca "commitado em 02/09". A diferença importa quando alguém for auditar isso depois.

E no dia seguinte ao lançamento, **24/11**, o Roger ganhou o que faltava para fechar a comparação:

- `review_comments[]` — cada apontamento com **arquivo:linha** e severidade **Important / Nit / Pre-existing**;
- política de aprovação em **observe-only**: ele sugere, não aprova;
- um comparador, para medir Roger contra outro revisor no mesmo diff;
- atestado `roger-qualidade.py`: **APTO 100/100**, selftest **46/46**, **10 testes novos**. Medido em 24/11.

## 4. Lado a lado

| | Claude Ship | Roger |
|---|---|---|
| Onde roda | GitHub + infraestrutura da Anthropic | self-hosted, em qualquer repositório |
| Review | inline por IA no PR | critic determinístico + evidence gate (nota 0–100, gaps com arquivo:linha) |
| Correção | PR Steward faz push das correções | não auto-corrige: handoff com causa, correção e rollback |
| Aprovação | Approvals pode aprovar (enforce) | só sugere (observe); humano decide |
| Cobrança | tokens da organização | zero por agente — uso os LLMs que já tenho |
| Auditoria | check run no GitHub | state + JSONL local + atestado |
| Lock-in | GitHub App, plano Team/Enterprise | zero |

## 5. Por que o Roger ganha

**Soberania.** Roda na minha máquina. Não preciso de GitHub App, de plano Team, nem de aprovar uma instalação no repositório de outra pessoa para revisar o meu próprio código.

**Decisão humana por arquitetura, não por configuração.** O Roger não aprova, não faz push, não mergeia, não deploya. Não é uma caixa que alguém desmarca numa tela de settings — a ausência dessas capacidades é o desenho.

**Veredito com evidência e fail-closed.** A nota vai de 0 a 100 e cada gap vem com arquivo:linha. Quando a medição falha, o resultado é bloqueio — 100/100 no atestado e 46/46 no selftest, medidos em 24/11, não uma promessa de README.

**Custo previsível.** Não há cobrança por agente. O gasto é o modelo que eu já pago, e o número não muda porque o repositório cresceu ou porque alguém abriu mais um PR.

**Auditável e reversível.** State, JSONL, locks, backup e rollback. Dá para reconstruir por que uma entrega passou, o que exatamente mudou e como voltar atrás.

O Ship tem polish e auto-fix prontos, e isso é vantagem real para quem vive dentro do GitHub. O diferencial aqui não é ter mais recurso — é ter menos superfície de decisão automática e mais previsibilidade sobre o que acontece com o meu código.

## 6. Próximos passos

O caminho agora é rodar o comparador em diffs reais e publicar o resultado com data de medição, incluindo os casos em que o Roger erra. Depois disso, o alvo é fechar o ciclo de observe-only com histórico de divergência: quantas sugestões o humano aceitou, quantas recusou e por quê. Um revisor que só reporta acerto não é auditável — é marketing.
