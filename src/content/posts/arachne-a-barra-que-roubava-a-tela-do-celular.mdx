Abri o Arachne no celular e a primeira coisa não foi o painel: era a barra de cima, com duas linhas e 117 pixels de altura num aparelho de 6 polegadas. No desktop, nada disso.

A correção virou um estudo de caso sobre duas armadilhas no mesmo sintoma: um reset de CSS genérico demais e um bloco de estilo que nunca compilou.

## O que estava acontecendo

A interface é uma aplicação de página única: barra superior com botão de comandos, coluna lateral de navegação e área de conteúdo. No celular, a coluna vira uma doca fixa embaixo e a barra deveria encolher para uma linha.

O primeiro commit do dia, às 02:47, media o estrago: 117 pixels. A causa não estava no componente da barra, e sim nos arquivos de reset, onde uma regra genérica para o elemento `header` forçava `flex-direction: column` em qualquer cabeçalho — inclusive no meu. A regra nasceu para o login e as páginas públicas, e por ser de elemento, não de classe, alcançava todos; no desktop ela nunca executava, porque vivia numa consulta de mídia para telas estreitas.

A segunda causa era mais humilhante. No componente Vue, um bloco de CSS estava escrito depois do fechamento da tag de estilo:

```css
/* o componente fechava o bloco de estilo aqui */
}

/* ──Mobile: respiro p/ navegação inferior ── */
@media (max-width: 768px) {
  .conteudo-principal {
    padding-bottom: 56px;
  }
}
```

Tudo depois do fechamento não é CSS do componente: é texto solto no template, ignorado em silêncio pelo compilador. O respiro que impedia a doca de baixo cobrir o último card nunca existiu — e ninguém reclamou, porque o sintoma era sutil: o fim da página ficava escondido, não ausente.

## Como foi resolvido

Primeiro, a barra voltou a ser uma linha. Em vez de brigar com o reset aumentando especificidade, o próprio componente passou a declarar a intenção inteira dentro da consulta de mídia:

```css
.barra-superior {
  flex-direction: row;
  flex-wrap: nowrap;
  align-items: center;
  gap: 8px;
  min-height: 52px;
}

.titulo-pagina {
  margin: 0;
  font-size: 0.92rem;
  font-weight: 600;
  white-space: nowrap;
  overflow: hidden;
  text-overflow: ellipsis;
  max-width: 150px;
}
```

O título da página entrou como elemento novo, limitado a 150 pixels e com reticências quando estoura — em vez de empilhar. O botão de comandos encolheu para um quadrado de 36 pixels e a altura medida caiu de 117 para 61 pixels. O bloco órfão voltou para dentro do componente e o respiro de 56 pixels passou a valer.

Três detalhes carregam a maior parte do valor: `min-width: 0` no contêiner do título, sem o qual o flexbox se recusa a encolher o filho e o ellipsis nunca dispara; `flex-wrap: nowrap`, que impede a segunda linha em vez de consertá-la depois; e `gap` explícito, porque sem ele os elementos colavam quando a etiqueta do atalho desaparecia.

## A doca, na mesma manhã

Às 03:14 veio a segunda frente: a doca de navegação do celular. No desktop ela tem 23 links e 58 pixels de altura; no celular, mostrar tudo era impossível. A solução foi reduzir a doca a quatro destinos principais, cada um com 56 pixels de altura e rótulo sempre visível — não só no toque, como era antes.

Aqui aparece um terceiro problema, clássico de especificidade: uma regra de mobile escondia todo link da doca que não fosse primário, então os quatro destinos continuavam invisíveis. A decisão de processo mais interessante foi comparar layouts sem branch: as variantes ficaram acessíveis por parâmetro na URL — quatro destinos rotulados no padrão, três mais um botão flutuante na segunda, doca anterior na terceira.

## O que isso muda

A lição não é sobre pixel: é sobre onde escrever a regra. Um reset de CSS por elemento é conveniente no dia em que nasce e caro seis meses depois, porque atravessa componentes que ainda não existiam. Quando um reset genérico briga com um componente específico, aumentar especificidade é o remédio errado — ou o reset respeita a fronteira, ou o componente declara a intenção inteira na própria consulta de mídia.

A segunda lição é sobre silêncio. O bloco órfão não gerou erro, aviso ou teste vermelho: gerou um layout levemente errado por semanas. As verificações automatizadas olhavam rotas e DOM renderizado, nenhuma media o CSS compilado num viewport estreito — um teste assim teria pego o defeito em minutos.

O terceiro ponto é o alvo de toque: os 36 pixels do botão compacto ficam abaixo do mínimo confortável de 44, e isso é escolha consciente, porque a doca de 56 pixels é o alvo principal de navegação.

## Próximo passo

As variantes são provisórias: existem para a auditoria visual e vão embora quando a decisão for tomada. O próximo passo é consolidar a variante aprovada como padrão do código e manter um teste de viewport estreita que meça a altura da barra — para que um reset global nunca mais empilhe o topo sem quebrar um teste antes de chegar no celular.
