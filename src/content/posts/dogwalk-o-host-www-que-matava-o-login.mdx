## O sintoma que parecia do banco

Cadastro não funcionava. Login não funcionava. O usuário preenchia o formulário, apertava o botão e recebia um erro genérico. Nada no banco, nada no log da API — porque a requisição nunca chegava lá.

O culpado estava na borda, num arquivo de três linhas que decidia quem podia falar com o backend.

O site é servido em dois endereços: `https://www.seu.pet` e `https://seu.pet`, sem o `www`. Para o navegador são origens diferentes — e o guard de CSRF das Pages Functions tratava só uma delas como legítima.

```js
// functions/_origins.js — como ficou depois da cura
export const ALLOWED_ORIGINS = [
  'https://patapass.pages.dev',
  'https://seu.pet',
  'https://www.seu.pet',
  'http://localhost:5173',
];
```

Toda requisição que muda estado — `POST`, `PUT`, `DELETE` — carrega o cabeçalho `Origin`. Se ele não está na lista, a função devolve `403 CSRF: Invalid origin` antes de qualquer lógica de negócio. O cadastro nunca acontecia porque a porta lateral estava fechada para o endereço que o usuário realmente digitava.

## O detalhe que separa um guard de um enfeite

A primeira versão da allowlist usava `startsWith` para comparar. Parece razoável e é um buraco.

Com comparação por prefixo, `https://seu.pet.atacante.com` passa no teste: começa com `https://seu.pet`, logo é "confiável". Um domínio de terceiro controlado por qualquer pessoa entrava pela porta da frente e o CSRF deixava de proteger coisa nenhuma.

A correção foi exigir igualdade exata, aceitando apenas a barra final como variação:

```js
export function isAllowedOrigin(origin) {
  if (!origin || typeof origin !== 'string') return false;
  return ALLOWED_ORIGINS.some((o) => origin === o || origin === `${o}/`);
}
```

Duas linhas de diferença. Uma delas transforma um guard em decoração.

## O bug que só aparecia no deploy

Existia ainda um terceiro problema, mais silencioso. O `_middleware.js` mantinha a própria cópia da lista de origins, inline, em vez de importar do `_origins.js`.

Resultado: o arquivo novo existia, os testes do arquivo novo passavam, e o middleware continuava usando a cópia velha. A correção estava no repositório e não estava no ar. Se o import quebrasse, o erro seria `ReferenceError` em runtime — no meio de uma requisição de usuário, não no build.

O conserto foi fazer o middleware importar a função testada:

```js
// functions/_middleware.js
import { isAllowedOrigin } from './_origins.js';
```

Agora existe uma fonte única. Se a allowlist mudar, muda num lugar e o teste cobre o mesmo arquivo que roda em produção.

## O que os testes travam

O teste não verifica "a função devolve booleano". Verifica as três fronteiras que importam:

- `https://www.seu.pet` é aceito — foi o endereço que quebrou em produção.
- `https://seu.pet` (apex) é aceito — os dois hostnames servem a mesma aplicação.
- `https://seu.pet.atacante.com` é barrado — o caso que a comparação por prefixo deixava passar.

Seis asserções, todas rodando contra o arquivo que o middleware importa de verdade.

## A lição que fica

Um controle de segurança tem duas metades: a lógica e o caminho até ela. A lógica estava certa e o caminho estava interrompido — e o sintoma não foi uma brecha, foi um produto que não deixava ninguém entrar.

A pergunta útil depois de escrever um guard não é "a função está correta?", e sim "quem chama essa função, e essa pessoa importa a mesma versão que eu testei?". Neste caso a resposta era não.
