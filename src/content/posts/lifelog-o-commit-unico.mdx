## O painel que sabia demais

No dia 8 de setembro, apertei o botão de publicar no painel de posts ocultos. A API virou `hidden: true` para `hidden: false` nos dois arquivos do par (português e inglês), commitou, deu push, deployou. Poucos minutos depois recarreguei o painel — e ele continuava listando o post que eu acabara de publicar. Lá fora, a página pública do post já respondia 200.

Nenhuma das fontes estava errada. Elas estavam descrevendo momentos diferentes do mesmo processo.

O problema não era o painel estar desatualizado — era desatualizado **por design**. A publicação estava coreografada como duas transações independentes:

```text
transaction 1: flip hidden:true -> false in <PT+EN pair>.mdx  -> commit -> push
transaction 2: regenerate api/ocultos-data.mjs without the pair -> commit -> push
```

Entre a transação 1 e a transação 2 existe uma janela. Dentro dela, o repositório diz uma coisa (post publicado, `hidden: false` nos arquivos mdx) e o índice gerado diz outra (post ainda na lista de ocultos). O painel em produção lê o índice do bundle deployado — que só muda no próximo deploy. Se a segunda transação cair com o commit depois do deploy da primeira, o painel congela no estado antigo até o deploy seguinte.

Eu chamei o sintoma de "painel listando um post já público" e tratei como bug do painel. Corrigir o sintoma era possível: regerar o índice no fim do fluxo, refazer o commit, disparar outro deploy. Foi o que fiz em `067da21` — e foi um curativo num corte que a cirurgia reabriria a cada publicação.

## O diagnóstico que doeu

A pergunta certa não era "por que o painel mente?" e sim "por que uma publicação são dois commits?".

A resposta honesta: porque cada commit sozinho é fácil. Virar o frontmatter é troca de string. Regerar um índice é ler um diretório e serializar JSON. Duas operações simples costuradas com dois commits — cada passo com seu próprio ponto de falha, cada falha no meio do caminho deixando o repositório num estado que só é meio verdade.

O índice `api/ocultos-data.mjs` é derivado dos frontmatters. Duas fontes de verdade derivadas da mesma origem, publicadas em momentos diferentes. Isso não é bug de sincronização — é uma garantia quebrada por design.

A correção que valia a pena não era sincronizar melhor os dois commits. Era commitar os dois como **um**.

## A coreografia do commit atômico

A API REST de conteúdo do GitHub (`PUT /contents`) substitui um arquivo por chamada. Não existe endpoint que commite três arquivos de uma vez nessa rota. O que resolve é a Git Data API — a camada de baixo nível em que um commit é um objeto com uma tree, e uma tree é um conjunto de referências a blobs.

A coreografia, em cinco chamadas:

```text
1. GET  /git/ref/heads/main            -> current commit sha (base)
2. GET  /git/commits/<base>            -> base tree sha
3. POST /git/blobs                      (one per file: PT mdx, EN mdx, index)
4. POST /git/trees                      (base_tree + the 3 blobs -> new tree)
5. POST /git/commits  (tree, parents=[base]) -> PATCH /git/refs/heads/main
```

O passo 4 é onde a mágica acontece: `base_tree` diz "comece da tree atual e mude só estes caminhos". O commit resultante carrega o repositório inteiro mais a mudança de três arquivos — e não existe momento intermediário em que `main` veja metade de uma publicação.

Em `scripts/ocultos-core.mjs`, a peça que fecha a coreografia:

```js
const treeSha = await createTree(baseTree, blobs);
const commit = await gh(`/repos/${owner}/${repo}/git/commits`, {
  method: 'POST',
  body: JSON.stringify({ message, tree: treeSha, parents: [baseSha] }),
});
if (commit.status !== 201) throw Object.assign(new Error(`commit HTTP ${commit.status}`), { status: commit.status });

const patch = await gh(`/repos/${owner}/${repo}/git/refs/heads/${branch}`, {
  method: 'PATCH',
  body: JSON.stringify({ sha: commit.data.sha, force: false }),
});
if (patch.status !== 200) {
  throw Object.assign(new Error(`ref update HTTP ${patch.status}`), { status: patch.status, moved: patch.status === 422 });
}
```

Dois detalhes ali carregam mais projeto do que parecem.

O `force: false` no PATCH é a proteção contra sobrescrita cega. Se outra sessão deu push de algo em `main` entre a minha leitura de `ref` e o meu PATCH, o GitHub responde `422` — a ref não é fast-forward. O erro não é tratado como falha genérica: ele vem etiquetado (`moved: true`) e o chamador entra num retry que **relê o conteúdo fresco de cada arquivo** do repositório antes de refazer a coreografia. Até três tentativas. A cada rodada, o novo estado do mundo entra na equação — nunca o meu snapshot desatualizado por cima do trabalho de outra pessoa.

E a regra de ouro: as fronteiras entre as chamadas não são pontos em que o repositório fica "meio publicado". São onde uma publicação **ainda não visível** se torna **única e completa**.

## Byte a byte igual ou nada

Commitar o índice junto com os arquivos mdx exige que o índice regerado na hora da publicação seja exatamente o que o build gera. Se o formato divergir em um único byte — um espaço, uma quebra de linha, uma ordem de chave JSON — toda publicação vira diff falso e o histórico do arquivo vira ruído.

A resposta foi uma única fonte de verdade de formato. `serializeOcultos` e `parseOcultos` vivem no mesmo módulo que o gerador do build consome; o endpoint de publicação importa exatamente os mesmos objetos. A propriedade é testável, e o teste diz exatamente isso:

```js
it('parse → serialize = bytes idênticos', () => {
  const text = serializeOcultos(samplePosts);
  const parsed = parseOcultos(text);
  expect(serializeOcultos(parsed)).toBe(text);
});
```

Quinze testes cobrem o contrato: cabeçalho gerado igual ao formato atual, parse aceitando um arquivo real com o ponto e vírgula final, parse falhando alto (e sem engolir) quando o marcador `export default` some, o flip preservando finais de linha LF e CRLF como estão, virar um arquivo já publicado sendo idempotente e devolvendo os bytes intactos, remover o par tirando PT e EN e preservando os demais, e as variantes de nomeação EN (`en/<slug>` versus `en/en-<slug>`, uma herança honesta das primeiras semanas) colidindo e deduplicando sem quebrar.

O detalhe que quase passou batido: virar `hidden: true` para `hidden: false` não pode normalizar finais de linha. O repositório tinha arquivos CRLF e LF convivendo, e um flip que padronizasse tudo viraria diff do arquivo inteiro — o commit atômico carregando renomeações invisíveis. `flipHidden` preserva o que está lá:

```js
export function flipHidden(raw) {
  const fmMatch = raw.match(/^---\r?\n([\s\S]*?)\r?\n---/);
  if (!fmMatch) return { raw, flipped: false, already: false, missing: true };
  const fm = fmMatch[1];
  const updated = fm.replace(/^(\s*hidden:\s*)true(\s*)$/m, '$1false$2');
  if (updated !== fm) return { raw: raw.replace(fm, updated), flipped: true, already: false };
  if (/^(\s*hidden:\s*)false(\s*)$/m.test(fm)) return { raw, flipped: false, already: true };
  return { raw, flipped: false, already: false, missing: true };
}
```

O regex do frontmatter aceita `\r?\n` nas bordas e preserva todo byte que não seja o `true` alvo. Um clique, um diff de uma palavra por arquivo.

## A publicação como transação

Depois do merge, uma publicação virou isto:

| Antes | Depois |
|---|---|
| 2 commits por publicação | 1 commit único |
| Janela com estado inconsistente em `main` | Nenhuma — `main` nunca vê metade |
| Painel podia listar um post já público | Índice e frontmatter saem no mesmo commit |
| Conflito com push concorrente = sobrescrever ou abortar | `422` detectado, conteúdo relido, retry até 3x |
| Formato do índice em dois lugares | Uma fonte, byte a byte igual por teste |
| Deploy do CI podia adicionar um commit extra de auto-cura | Deploy do CI só cura divergência de qualquer origem |

O deploy também ganhou uma rede: se o build roda num estado em que o índice diverge do HEAD, o próprio workflow commita o alinhamento e segue. Não era para acontecer — o commit atômico garante que não acontece no caminho normal —, mas um sistema que só funciona quando tudo dá certo é um sistema que já mentiu para você uma vez e está esperando a próxima.

O que ficou de lição não é a Git Data API em si — a documentação dela é boa e a coreografia está em qualquer guia de commit multi-arquivo. A lição é a ordem das perguntas. Eu tinha dois commits porque dois commits eram fáceis, e o estado inconsistente entre eles era "temporário", "só alguns segundos", "ninguém clica nessa janela". Estados temporários não são inofensivos: são garantias em espera. Quando duas fontes de verdade derivam da mesma origem, elas precisam sair juntas — no mesmo commit, no mesmo deploy, no mesmo instante. Ou viram uma só.
