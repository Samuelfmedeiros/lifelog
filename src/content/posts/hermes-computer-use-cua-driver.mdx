O Hermes sempre teve computer use. Desde o começo, uma das ferramentas mais ambiciosas do agente: controlar o mouse e teclado do computador como um humano faria.

Na prática, era uma aposta. Clicava no lugar errado, o tipo perdia contexto, a permissão do gateway quebrava. Funcionava às vezes — o suficiente pra mostrar potencial, não o suficiente pra confiar.

## Três problemas, um sistema

O computer use do Hermes é um sanduíche de três camadas: o gateway (que recebe o comando), o cua-driver (que executa no SO), e o agente (que decide o que fazer). Cada camada tinha seu próprio problema.

### 1. Permission modes desalinhados

O cua-driver 0.10 introduziu um sistema de permission modes: `standard`, `explicit`, `yolo` — cada um com um nível diferente de restrição pra clicar, digitar, capturar tela. O problema é que o gateway do Hermes usava um namespace diferente pra session-key, então quando o agente dizia "modo standard", o driver recebia "modo none" e bloqueava tudo.

```
Gateway salva session-key como:
  user:default:session:abc123

cua-driver 0.10 espera:
  user::session:abc123

Nunca batem → permissão negada → clique não acontece
```

O commit `871404095` resolveu: alinhar o namespace de session-key entre gateway e driver.

### 2. Desktop control sem roubar foco

Esse era o mais frustrante. Quando o Hermes clicava em algo, o foco do mouse pulava pro alvo — eu perdia o que estava fazendo. O commit `94d1dff50` introduziu o roteamento de desktop control: o driver agora roteia a entrada pro app certo sem trazer a janela pra frente.

```typescript
// Antes: clicar no VSCode trazia ele pro primeiro plano
computer_use.click({ element: 14 })
// → VSCode ganha foco, seu cursor desaparece

// Depois: o clique chega no VSCode, mas seu cursor nunca sai do lugar
computer_use.click({ element: 14 }, { delivery_mode: 'background' })
// → VSCode recebe o clique, você continua trabalhando
```

O segredo é o `delivery_mode: 'background'` — o input chega no processo alvo, mas o sistema operacional não troca o foco. Parece mágica, mas é só usar as APIs de accessibility corretas do Windows/Linux.

### 3. Full-duplex voice barge-in

Esse foi um extra que veio junto: `e0233f8fc` — voice barge-in full-duplex. Antes, se o Hermes estivesse gerando uma resposta e eu falasse "para", ele terminava de falar primeiro. Agora a captura de áudio é full-duplex: ele escuta enquanto fala.

Na prática, isso significa: "Hermes, abre o VSCode na pasta do Dogwalk" → ele começa a responder "Claro, vou abrir..." → "Não, na verdade na pasta do Arachne" → ele interrompe e corrige o caminho.

Parece detalhe, mas full-duplex muda a sensação de conversa. De turn-taking (cada um espera sua vez) pra interrupção natural (como duas pessoas conversando).

## O ganho real

Depois desses três fixes, o computer use passou de "funciona às vezes" pra "confiável o suficiente pra delegar".

Hoje eu faço:

```
"Hermes, abre o Playwright report do último teste do Dogwalk"
→ Ele abre o VSCode, navega até o projeto, abre o report HTML, tira um screenshot
→ Tudo em background — meu cursor nunca sai do lugar

"Hermes, clica em 'Create Pull Request'"
→ Ele vai no GitHub, preenche o formulário, submete o PR
→ Eu continuo codando
```

Cada fix individual parece pequeno. Um namespace, um delivery_mode, um full-duplex. Juntos, transformaram uma ferramenta experimental em algo que eu uso todo dia sem pensar.
