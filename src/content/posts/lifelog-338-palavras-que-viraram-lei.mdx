## A nuvem de tags virou babilônia

A nuvem de tags do arquivo era um espelho do maior pecado do blog: cada
post nascia livre para inventar a própria taxonomia. "automacao" aqui,
"automation" ali, "Automação" acolá — três chips apontando pra conceitos
que na minha cabeça eram um só. A página `/tag/<slug>` da Opção C
finalmente existia, mas alimentada por um pântano: 336 slugs vivos e nada
impedindo o próximo post de criar o 337º com typo.

O gatilho da campanha foi um post do Dogwalk. Eu escrevi o frontmatter na
convicção — tags [pwa, service-worker, offline, workbox, front] — e o CI
quebrou na esteira. A checagem antiga só gritava depois do push. Verificação
de vocabulário não é report de build, é porta de entrada: precisa reprovar
antes do merge, senão a exceção de ontem vira a regra de hoje.

## A decisão: um vocabulário, duas línguas

A Opção C venceu as outras duas com um argumento simples: quem mantém o
vocabulário é o mesmo código que o consome. A fonte de verdade virou um
arquivo TypeScript que a UI importa direto — zero desvio entre o que o
guardião valida e o que as chips renderizam. Sem espelho manual, sem drift.

A regra de língua foi a parte que mais gerou discussão comigo mesmo. Slug
canônico em inglês (língua franca técnica), mas com label em português
para exibição: o slug é `security`, o visitante lê "Segurança". A variante
em português nunca vira slug — vira alias, apontando pro canônico. Um
conceito, um slug, N caminhos de entrada.

```typescript
export const TAG_VOCAB: TagDef[] = [
  { slug: 'security', pt: 'Segurança' },
  { slug: 'automation', pt: 'Automação' },
  // ...
]

export const TAG_ALIASES: Record<string, string> = {
  'seguranca': 'security',   // variante PT = alias, nunca slug
  'automacao': 'automation',
}

export function canonicalizeTag(tag: string): string {
  const key = tag.trim().toLowerCase().replace(/_/g, "-").replace(/\s+/g, "-");
  const c = TAG_ALIASES[key] ?? key;
  return c in TAG_ALIASES ? TAG_ALIASES[c] : c;
}
```

## O guardião que fala a mesma língua

O guardião no CI é um script Python — e a parte que me dava calafrio era
a duplicação: se o validador lê o vocabulário de uma cópia, o drift entre
as cópias vira bug silencioso. A solução foi o guardião **parsear o
próprio .ts**: regex extrai os slugs e os aliases direto do arquivo que a
UI consome. Uma fonte de verdade, dois consumidores.

Os códigos de erro viraram um mini-dicionário do que dá errado em
taxonomia: E1 (tag fora do vocab), E2 (tag do projeto ausente — a
structural), E3 (PT e EN divergentes), E4 (tags multi-line, que quebram
o parse do frontmatter), E5 (duplicata no mesmo post), E6 (project fora
do vocab). Com `--strict`, qualquer E reprova o deploy.

```yaml
# .github/workflows/deploy.yml — quality gates, antes do build
- name: PT/EN Sync check
  run: python3 scripts/check-lang-sync.py
- name: Tag vocabulary check (Opção C)
  run: python3 scripts/check-tags.py --strict
```

E uma lição de CI que custou uma rodada: o guardião mora no repositório,
mas o CI roda no runner do GitHub — path absoluto da minha máquina quebrava
tudo no checkout. `ROOT = Path(__file__).resolve().parents[1]` resolve
relativo ao script e funciona nos dois mundos.

## 269 arquivos em uma migração

Com vocabulário e guardião prontos, faltava a parte mais chata: os posts
existentes. A migração tocou 269 arquivos PT e EN — canonicalizar aliases,
garantir a tag structural do projeto, unificar PT/EN, deduplicar, e
achatar tudo pra uma linha no frontmatter (tags multi-line eram outro
veneno silencioso de parse).

O critério de paridade foi o detalhe que fez a migração valer: PT e EN do
mesmo post passam a ter slugs **idênticos**, na mesma ordem. A página
/tag/security mostra o mesmo conjunto de posts nas duas línguas — se um
dia divergirem, o E3 acusa no CI.

## O que sobrou aprendendo

**A comparação que fechou a decisão:** as opções A e B tratavam tags como
texto livre com dicas; a Opção C trata como schema. A diferença apareceu
no primeiro post novo depois do guardião — eu tentei `front` de cabeça, o
guardião apontou o canônico (`frontend`), e o conceito novo (`metadata`,
`taxonomy`) entrou no vocab no MESMO commit do post que o usa. Conceito
novo sem entrada no vocab = CI vermelho. A legislação cresce junto com a
cidade, nunca depois.

**Conceito novo é decisão de design, não typo corrigido na hora.** O
momento de adicionar um slug é o mesmo do post que o introduz — forçou a
pergunta "isso é um tema recorrente ou um caso único?" 336 slugs depois,
o vocabulário segue canônico, bilingue e sob guarda.
