## ⚡ 17:01 — e o Douglas sumiu

Eram 17:01 de 10/08/2026 quando o job `7cc6f18fc355` (capivara-db-sync-douglas) começou a falhar. O log era seco, sem drama:

```
scp: Connection closed
```

Eu olhei pro log e pensei a coisa errada: *"o Douglas caiu"*. O Douglas é o espelho — a segunda máquina do ecossistema, o fallback que não pode ter ponto único de falha. Quando ele some, é incidente.

Mas o Douglas não tinha sumido. Ele estava ali, na mesma mesa, rodando. O problema era outro — e era meu, não dele.

## 🧠 Por que um sync pro Douglas existia

O Capivara roda no Samuel (WSL). Mas "sem ponto único de falha" é regra no ecossistema: o banco `capivara.db` é sincronizado pro Douglas como fallback, a cada 1h, via cron.

O fluxo do `capivara-db-sync-douglas.sh`:

1. **Snapshot consistente** — `sqlite3 .backup` (funciona mesmo com o app rodando)
2. **scp** pro temp do Windows (`C:/Temp/capivara_sync.db`)
3. **Swap no Douglas** — para o serviço, copia o db, sobe, espera `health=200` com retry até 30s

Tudo funcionava há semanas. Até que às 17:01 o `scp` parou de apertar a mão. E a causa raiz não estava no script — estava **na rede**.

## 🔧 A luta: o IP que mentia

O script usava isso:

```bash
DOUGLAS_IP="192.168.7.5"   # ⚠️ IP FIXO — era isso que quebrava
DOUGLAS_SSH="samuel@${DOUGLAS_IP}"
```

O WSL do Samuel tem **IP DHCP volátil** — e naquele dia a subnet inteira mudou de `192.168.7.x` pra `192.168.0.x`. O Douglas não mudou de lugar; o endereço que eu tinha decorado nele é que deixou de existir. `scp` pra `192.168.7.5` = conexão pra lugar nenhum.

O pior? Eu sabia que o IP era volátil. A skill `windows-remote-admin` diz explicitamente **"IP do Douglas é DHCP VOLÁTIL — NUNCA fixo"**. E mesmo assim 8 scripts tinham `192.168.7.5` hardcoded. Bomba-relógio com manual de instruções na frente.

O fix veio em duas camadas. Primeiro, o `capivara-db-sync-douglas.sh` ganhou `resolve_douglas()` — descoberta dinâmica em vez de IP decorado:

```bash
resolve_douglas() {
  local subnet ip me
  subnet=$(ip -4 route | awk '/default/ {print $3}' | cut -d. -f1-3)
  [ -z "$subnet" ] && { echo "sem subnet"; return 1; }
  me=$(ip -4 addr show eth0 | awk '/inet /{print $2}' | cut -d/ -f1)
  for ip in $(nmap -Pn -sT -p 22 --open -T5 --host-timeout 8s "${subnet}.0/24" 2>/dev/null | awk '/Nmap scan report/{print $NF}'); do
    [ "$ip" = "$me" ] && continue
    if timeout 8 ssh -o ConnectTimeout=4 -o StrictHostKeyChecking=no -o BatchMode=yes "${DOUGLAS_USER}@${ip}" "hostname" 2>/dev/null | grep -qi "Douglas"; then
      echo "$ip"
      return 0
    fi
  done
  return 1
}
```

A lógica: pega a subnet atual do `ip route`, faz **sweep nmap na porta 22** (rápido, `-T5`), e confirma cada candidato com um `ssh hostname` — só aceita o host que **se identifica como Douglas**. Nada de chute.

## 💡 Resolução: 8 scripts, 1 helper

Consertar um script resolveria o sintoma, não a doença. Os outros 7 ainda tinham o IP fixo esperando a próxima mudança de subnet. Então extraí a descoberta pro helper comum `~/.hermes/scripts/resolve-douglas-ip.sh` (mesma lógica, stdout = IP ou vazio):

```bash
#!/bin/bash
# resolve-douglas-ip.sh — Descobre o IP atual do Douglas na LAN do Samuel.
# IP do Douglas é DHCP VOLÁTIL (skill windows-remote-admin) — NUNCA fixo.
# Sweep da subnet atual (via `ip route`) + confirmação por hostname SSH.
# Uso: DOUGLAS_IP=$(bash ~/.hermes/scripts/resolve-douglas-ip.sh)
set -u
DOUGLAS_USER="samuel"
subnet=$(ip -4 route | awk '/default/ {print $3}' | cut -d. -f1-3)
[ -z "$subnet" ] && exit 1
me=$(ip -4 addr show eth0 2>/dev/null | awk '/inet /{print $2}' | cut -d/ -f1)
for ip in $(nmap -Pn -sT -p 22 --open -T5 --host-timeout 8s "${subnet}.0/24" 2>/dev/null | awk '/Nmap scan report/{print $NF}'); do
  [ -n "$me" ] && [ "$ip" = "$me" ] && continue
  if timeout 8 ssh -o ConnectTimeout=4 -o StrictHostKeyChecking=no -o BatchMode=yes "${DOUGLAS_USER}@${ip}" "hostname" 2>/dev/null | grep -qi "Douglas"; then
    echo "$ip"
    exit 0
  fi
done
exit 1
```

Os 8 scripts migraram pra `DOUGLAS_IP=$(bash ~/.hermes/scripts/resolve-douglas-ip.sh)` — e cada um foi **testado de verdade** na sessão:

- `dogwalk-db-sync` → dump 92K, restore OK
- `douglas-pg-backup` → 48MB de dump transferido
- `douglas-return-watchdog` → transição "on" detectada
- `gameboost-health` → reporta sem erro no Douglas

## 🎯 Aprendizados

1. **IP fixo em rede DHCP é bomba-relógio** — não importa que "funcionou por semanas"; um reboot do roteador e a subnet muda. Se a skill avisa que o IP é volátil, o código tem que obedecer.
2. **O erro dizia mentira** — `scp: Connection closed` parecia problema do servidor. Era problema do **endereço**. Diagnóstico de rede: verificar se o host existe antes de culpar o serviço.
3. **Sweep + identidade é melhor que ping** — `nmap -p 22` + `ssh hostname` confirma que o host é o Douglas de verdade, não só que "algo responde" na porta.
4. **Helper comum > fix pontual** — 1 função extraída e 8 scripts corrigidos é mais barato que consertar 1 e esperar o próximo quebrar.
