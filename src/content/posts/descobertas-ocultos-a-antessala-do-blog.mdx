## A rota que funcionava no meu laptop

Todo site com moderação tem, em algum lugar, uma página que só o dono deveria ver: o que espera decisão. A minha listava o conteúdo pendente do blog — e funcionava perfeitamente no `pnpm dev`. No deploy, devolvia lista vazia. Sempre. Sem log de erro, sem stack trace, só vazio.

A primeira linha de código daquela rota era inocente:

```javascript
// o que eu escrevi primeiro — funciona local, quebra no deploy
import { readdirSync } from 'fs'
const dir = path.resolve(__dirname, '../src/content/posts')
```

Local, o `__dirname` aponta pro diretório certo: o código roda de dentro da árvore do repositório, e os arquivos estão dois níveis acima. Foi exatamente essa suposição que quebrou no deploy.

## O bundle não preserva a árvore do repositório

Num deploy serverless, o código da rota é *empacotado*: as funções são bundladas num diretório de chunks, longe de qualquer `src/content/`. O `__dirname` que no meu laptop apontava pra árvore do repo, no deploy apontava pra uma pasta que nunca vai ter um arquivo de conteúdo dentro.

E o pior veio da minha própria "robustez": o `try/catch` que eu coloquei em volta da leitura engoliu a exceção e devolveu lista vazia. O pior tipo de falha não é a que explode — é a que se disfarça de ausência de dado. A página dizia "nada pendente", quando a verdade era "a leitura nem aconteceu".

Lição registrada: se um erro é tratável, trate com log barulhento; se não é, deixe-o propagar. Silêncio não é robustez, é sabotagem contra o seu eu do futuro.

## A saída: congelar o dado no build

A correção veio de um princípio que o próprio gerador estático já ensina — se o dado é conhecido no build, não existe justificativa pra redescobri-lo em runtime:

```javascript
// scripts/gen-dados.mjs — roda ANTES do build
// 1. varre a árvore de conteúdo com gray-matter (parseia só o frontmatter)
// 2. extrai slug, título, data e projeto de quem casa com o critério
// 3. escreve api/dados.mjs: export default [ ...itens ]
```

A rota serverless deixou de tocar filesystem e virou um `import`. O dado viaja *dentro* do bundle, gerado por quem tem contexto completo: a máquina de build. O `__dirname` — a peça frágil — desapareceu do código de runtime inteiro.

| | Ler em runtime | Congelar no build |
|---|---|---|
| `__dirname` | aposta geográfica | nem existe |
| Origem do dado | servidor, na hora | máquina de build |
| Falha típica | lista vazia silenciosa | build quebra na sua frente |
| Custo por request | leitura + parse | import estático |

A coluna do meio não é só lenta — é *insegura*. A da direita falha cedo e alto, que é onde uma falha deve falhar.

## O painel de moderação que ganhou um balcão de reclamações

Com o dado congelado, a página de moderação ficou o que sempre deveria ter sido: uma lista do que espera decisão e um botão por item. O próximo passo já tá no ar — o botão de "recusar" num post reprovado abre uma issue no repositório, com o motivo escrito na hora, e devolve o item pra fila de revisão.

O loop fechou: o pipeline produz, a página lista, a decisão de volta vira artefato rastreável no repositório. Moderar deixou de ser ritual de terminal e virou dois toques — com trilha de auditoria de brinde.
